# 修复原理与修改方法

## 1. 原机故障不是单一的“少报几个格式”

AC3、EAC3 原本可用；DTS/TrueHD/DTS-HD 在 Android API、策略、HAL 格式处理、封装、硬件配置和供数缓冲上有多层缺口。只改能力声明会出现能选音轨但无声、快进、功放偶尔点亮或持续断音。

下文前六项代码/策略修复及新增客户端堆配置，共七个最终文件，其原件 SHA 以 `manifests/active-files.json` 为准；以下地址均为这一版固件的地址，不能当成同 SoC 通用偏移。

## 2. AudioPolicy：开放普通 DIRECT 压缩通路

修改 `/vendor/etc/audio_policy_configuration.xml`：新增 `direct raw` mixPort，flags 为 `AUDIO_OUTPUT_FLAG_DIRECT`，使用动态 `<profile name=""/>` 从 HAL 查询真实能力；在原 HDMI Out route 的 sources 中追加 `direct raw`。

保留原 HW_AV_SYNC、PCM、蓝牙等端口，不删除官方原有路径，不伪造 EDID。具体文本差异见 `patches/audio-policy.diff`。

## 3. HAL：能力查询和保留真实压缩格式

源码 `src/hal/hal_channels.c`、`src/hal/hal_hooks.S`；构建入口 `scripts/build_hal.py`。

- 在原能力查询处增加 HD 声道补充，读取实际 HDMI `aud_cap`：TrueHD 对应 MAT，DTS-HD 对应 DTS-HD；按真实最大声道数提供 5.1 / 6.1 / 7.1。
- 原格式白名单会把 HD 格式落回 PCM；只在 EDID 确认支持时保留 TrueHD / DTS-HD，其他格式保持原分支。
- 保持已有 ELF load 段的虚拟地址、文件偏移与厂商代码；复用 PT_NOTE 的程序头槽新增 RX 段。不是覆盖整个 HAL 的实现。
- 最终 HAL 新段 VA `0x7c000`、文件偏移 `0x7d000`，1754 字节。十个原 4 字节跳转/调用点加一处延迟表常量，完整记录见 `verification/hal-patch.json`。

## 4. 封装库：完整码流装入 HDMI 载波

修改 `/vendor/lib/libdroidaudiospdif.so`，不是新增系统解码器。源码位于 `src/spdif/`，编译 API28 ARMv7。

- AOSP 兼容 SPDIFEncoder 外壳保留本机 C++ 导出符号、虚表和对象 ABI；实机探针确认基类大小 `0x30`。
- 原始参考实现中的其他 ROM 分配大小注释不能代替本机 ABI；本机结果见 `verification/packer-abi.json`。
- AC3 / EAC3 根据完整 sync frame 长度复制负载并生成 IEC 61937 头。修复 AC3 起始 burst preamble、EAC3 第一组六块边界；完整已输出 EAC3 burst 与 FFmpeg 前缀一致。
- 普通 DTS core 保持原格式。满周期 DTS/WAV 帧没有额外头空间时遵循 FFmpeg 行为，不截断、不硬塞 IEC 头。
- TrueHD 采用 FFmpeg MLP parser 与 SPDIF muxer 构造 MAT。DTS-HD 采用 DCA parser 与 SPDIF muxer，保留 core + EXSS。
- 解析器只分帧；`submit_frame()` 完整复制解析帧后 `av_write_frame()`，不调用解码/混音/重编码接口。
- DTS 被应用标作普通 DTS 时，首帧 core 的**准确结束边界**出现 EXSS 才选择 HD 封装。不是搜索 payload 任意字节。
- seek 后孤立 DTS EXSS 不当作完整音频单元；reset 丢弃旧时间线的不完整帧，避免拼接。当前边界实现在受支持流型内工作，不宣称覆盖所有 LE/14bit/96k 变体。
- 禁用逐字节 VERBOSE；保留必要告警/错误。

实际链接冻结 FFmpeg **n8.1.3**，提交 `1041abdc962f4cc4f394aa8de9dc5236c0c3b9e7`，不是解码项目所用 n6.1.1。静态库、生成配置和完整源包见 third_party/；本次在本机重编适配层并重新链接冻结库，没有声称从零重编整套 FFmpeg。

## 5. Android 9 框架：允许 TrueHD encoding 14

原 `AudioFormat` 的 public/valid、linear frames、linear PCM 和 Builder 表没有正确接纳 TrueHD，飞牛因此无法选择/建立 TrueHD AudioTrack。

对原 `boot-framework.oat` 与 `boot-framework.vdex` 中相同的四张共享 switch 表修改 encoding 14 的目标分支。public 和 valid 共用实现，所以覆盖五个方法只涉及四张表。两个文件**各四字节、总八字节变化**。

保留原文件大小、原 framework.jar、DEX/OAT 身份、其他 boot 依赖、栈映射和原预编译 APK 缓存。精确偏移、前后值见 `verification/framework-table-patch.json`，代码在 `scripts/patch_framework_tables.py`。

这是绑定本机旧优化产物的原位补丁，不是通用 Android9 framework 替换包，也不是修复其他 ROM 的正式系统构建方法。

## 6. TrueHD / DTS-HD：时钟和延迟的单位必须一致

原 HAL 将封装后的 TrueHD 字节数除以4计内容帧；MAT/HBR 的本机对应关系需要除以64。错误让播放位置约快16倍，导致画速异常、反复自动暂停/恢复及无声。

- 以 64 位累计封装字节数计算：HD `/64`，保留原流基线，避免32位截断。
- HD 内容帧延迟接口使用硬件延迟 `/16`。
- 毫秒接口与上述接口独立：先 `/4`，再按 nominal 192k 换算，不能统一套同一个除数。
- presentation 调用扣除内容帧，不能把毫秒值当作帧数。
- 保留 AC3 / EAC3 / 普通 DTS 的原计数规则。

ALSA 使用 HBR 192k 配置；本机 S16 双载波路径观测有效 DMA 约768k物理帧/秒。这些载波计数不是影片的48k内容采样率。

## 7. 物理硬件缓冲与 pause/resume

TrueHD / DTS-HD 物理队列采用 period_size=4096、period_count=8，总32768物理帧，以本机 S16 双载波声道计131072字节，约43ms。此处已经达到确认过的驱动 `buffer_bytes_max=131072`。

不能再照 Android12 环境配置65536物理帧：本机明确返回 EINVAL。普通 DTS core 队列保持原值。

原 AUGE 硬件恢复会发 PREPARE，频繁 pause/resume 会清掉部分 MAT ring。对**普通 DIRECT** TrueHD/DTS/DTS-HD撤销可选硬件 pause/resume 回调，使用 Android9 自带的软件回退；不改变 HW_AV_SYNC 路径和其他格式能力。本机 TrueHD 状态辅助函数还会区分 PREPARED/RUNNING/PAUSED/XRUN，避免重置本可继续的 ring。

## 8. DTS-HD 被标成 DTS：封装和 HAL 必须同时匹配

实际飞牛请求 DTS `0x0b000000`、7.1、48k，但数据含 EXSS。封装器发现 EXSS 后若 HAL 仍按普通 DTS/48k/小队列送出，功放不能稳定接收 DTS-HD。

在 `out_write_direct` 原锁内加入有限状态检测：跨写调用检查准确 core 边界后的 EXSS；真实 EDID 允许时将**内部**格式升级为 DTS_HD `0x0c000000`，配置192k HBR和对应计数/缓冲。应用公开格式和计数基线保留。

状态只使用 stream standby 后已核对的3字节 padding，不扩大对象、不加全局队列/线程。需要重建输出时调用原**不加锁内部** standby `0x1b8e4`，不能递归调用会加锁的公开 out_standby_direct。

当前升级限定普通48k裸BE DTS，排除 tunnel/HW_AV_SYNC、已封装输入及96k；不宣称所有 DTS-HD 变体都覆盖。无EXSS的 DTS-ES6.1 `mask0x13f` 保持普通 DTS 载波，不因7声道掩码误升HD。

## 9. 最终连续断音：AudioFlinger 编码共享队列过小

只增硬件队列仍会连续断音：原请求的应用 AudioTrack 共享队列约4104编码字节，系统 getMinBufferSize 为2052。AOSP9 的普通 PCM 分支有最低容量计算，非比例压缩音轨却直接接受非零请求，供数余量不足。

最终在 `/system/lib/libaudioflinger.so` 的 `PlaybackThread::createTrack_l` 入口设置服务端下限：

- 普通 streaming DTS / DTS_HD / TrueHD：`*pFrameCount = max(*pFrameCount, 131072)`。
- **此处一个 frame 是一个编码字节**，因此是128KiB压缩数据；不是PCM样本，不是再增加DMA帧数。
- 保留更大的应用请求；排除非目标格式、静态 shared buffer、HW_AV_SYNC `0x40`、COMPRESS_OFFLOAD `0x10`。
- 应用拿到服务端返回的实际容量，不加额外异步写线程，不修改应用代码。

原函数 VA `0x1df38`，文件偏移 `0x17f38`；原4字节 prologue 替换为 Thumb 分支，新增96字节RX段 VA/offset `0x54000`。ARM32 非平凡 `sp<Track>` 返回含隐藏R0，this在R1，format在原SP+8、pFrameCount在+16、shared引用+32、flags指针+40。必须核对本机反汇编，不能套A12或64位ABI。

源码 `src/flinger/flinger_buffer.S`，构建 `scripts/build_flinger.py`。240种实际Thumb执行用例验证寄存器、栈、格式、标志、静态缓冲与容量；实机只构造/查询/释放AudioTrack、不play/write，确认DD/DD+仍4104，DTS/DTS_HD/TrueHD的5.1/6.1/7.1实际容量131072。最终用户再次验证TrueHD和DTS-HD MA7.1正常。

## 10. Atmos：保留码流与通过验收是两回事

DD+ JOC与TrueHD Atmos扩展位于编码码流内部。当前封装保留完整帧，没有删除对象子流、提取普通7.1或解码重编码的代码，因而从代码上支持元数据随码流保留。TrueHD封装里的MAT是编码TrueHD的传输封装，不等于将音轨转为普通PCM。

播放器仍须交出完整原始码流；不能恢复上游已丢弃的信息。E_AC3_JOC单独API格式协商、真实带对象样本的逐字节闭环、功放Atmos识别尚未全部验证，不能把普通DD+/TrueHD验收等同于Atmos实测通过。当前功放无Atmos能力，所以只给代码分析结论，不伪造EDID来宣称通过。
